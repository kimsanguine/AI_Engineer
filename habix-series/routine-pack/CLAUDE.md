## 변형 A — PM 버전

> **메모.** **이 CLAUDE.md는 우리 프로젝트의 시스템 오브 레코드(System of Record)입니다.** 채팅창에 쓴 지시는 사라지지만, 이 파일은 다음 세션의 시작점이 됩니다. 50~80줄을 넘기면 *주제별 문서로 분리*하세요.

### 1. 프로젝트 한 줄 정의
제품 스펙 문서를 일관된 포맷으로 정리하고, 회의록을 의사결정/액션아이템 단위로 요약하는 PM 보조 에이전트 프로젝트입니다.

### 2. 사용 도구 스택
- 에디터: Cursor 또는 Claude Code
- 문서: Notion (스펙 DB), Google Docs (회의록 원본)
- 작업 관리: Linear 또는 노션 보드
- 통신: Slack (요약 게시용)

### 3. 절대 하지 말 것 (하드 제약)
- 회의록 원본 파일을 직접 수정하지 마세요. 항상 사본을 만든 후 작업합니다.
- 외부 고객사명, 매출 수치는 요약본에 그대로 노출하지 마세요. 마스킹 후 게시합니다.
- 스펙 문서의 「의사결정 로그」 섹션은 사람이 확정한 내용만 적습니다. 추정 금지.
- 슬랙에 자동 게시할 때 `@channel`, `@here` 멘션 절대 금지.
- 5장 이상의 첨부 파일을 한 번에 처리하지 마세요. 분할해서 처리합니다.

### 4. 자주 하는 작업과 검증 방법
- 회의록 요약: 원본 길이의 10퍼센트 이하로 줄이고, 액션아이템 표가 포함되었는지 확인합니다.
- 스펙 초안 작성: 「배경/목표/비목표/성공 지표」 4개 헤더가 반드시 있는지 확인합니다.
- 주간 우선순위 정리: 항목별로 담당자와 마감일이 비어 있지 않은지 확인합니다.

### 5. 폴더/파일 컨벤션
- `/specs/YYYY-MM-DD_기능명.md` — 스펙 문서
- `/meetings/YYYY-MM-DD_회의제목.md` — 회의록 요약본
- `/decisions/decision-log.md` — 누적 의사결정 로그

### 6. 세션 시작 시 항상 확인할 것
- `decisions/decision-log.md` 최근 3건을 먼저 읽습니다.
- `progress.md` 마지막 항목을 읽고 어제 막힌 곳부터 시작합니다.

### 7. 세션 종료 시 항상 남길 것
- `progress.md`에 오늘 한 일/막힌 곳/내일 첫 작업을 기록합니다.
- 새 의사결정이 있었다면 `decision-log.md`에 한 줄 추가합니다.

### 8. 사람의 승인이 필요한 작업 (휴먼 인 더 루프)
- 스펙 문서의 「범위(Scope)」 변경
- 외부 발송이 포함되는 모든 결과물 (슬랙 게시, 이메일 발송)
- 의사결정 로그에 새 항목을 추가하기 직전

## 변형 B — 1인 빌더 버전

> **메모.** **이 CLAUDE.md는 우리 프로젝트의 시스템 오브 레코드입니다.** 채팅창에 쓴 지시는 사라지지만, 이 파일은 다음 세션의 시작점이 됩니다. 50~80줄을 넘기면 *주제별 문서로 분리*하세요.

### 1. 프로젝트 한 줄 정의
Lovable로 생성한 SaaS MVP의 인증/결제/이메일 흐름을 보완하고, 실제 사용자 데이터를 다룰 수 있게 백엔드를 안정화하는 1인 빌더 프로젝트입니다.

### 2. 사용 도구 스택
- 프론트엔드: Lovable 생성 코드 (수정 최소화)
- 백엔드/DB: Supabase
- 결제: Stripe (테스트 모드 우선)
- 이메일: Resend 또는 동등 서비스
- 배포: Vercel

### 3. 절대 하지 말 것 (하드 제약)
- `main` 브랜치에 직접 푸시 금지. 항상 브랜치를 따고 PR을 만듭니다.
- Stripe 라이브 키를 코드에 적지 마세요. 환경변수만 사용합니다.
- 실서비스 DB 테이블에 `DROP`, `TRUNCATE`를 실행하지 마세요.
- 사용자 비밀번호 평문 로깅 금지.
- Lovable이 생성한 파일을 일괄 리팩토링하지 마세요. 변경 범위는 한 번에 한 화면만.

### 4. 자주 하는 작업과 검증 방법
- 새 API 라우트 추가: 로컬에서 성공/실패 경로를 각각 한 번씩 호출해 응답 코드를 확인합니다.
- DB 스키마 변경: 마이그레이션 파일을 만들고, 롤백 SQL을 함께 작성합니다.
- 결제 이벤트 처리: Stripe 테스트 카드로 결제 성공/실패/환불 3가지를 모두 통과시킵니다.

### 5. 폴더/파일 컨벤션
- `/app` — Lovable 생성 코드 (가급적 보존)
- `/server` — 직접 작성한 API 라우트
- `/db/migrations/` — 마이그레이션 SQL
- `/scripts/` — 일회성 작업 스크립트

### 6. 세션 시작 시 항상 확인할 것
- `feature_list.json`에서 state가 `failing` 또는 `blocked`인 항목을 먼저 확인합니다.
- 환경변수가 모두 로컬에 세팅되어 있는지 확인합니다.

### 7. 세션 종료 시 항상 남길 것
- 변경한 파일 목록과 그 이유를 `progress.md`에 기록합니다.
- 새로 추가된 환경변수가 있다면 `.env.example`에 키만 추가합니다.

### 8. 사람의 승인이 필요한 작업 (휴먼 인 더 루프)
- 결제 라이브 모드 전환
- DB 스키마 변경 적용 (개발 → 운영)
- 사용자에게 발송되는 트랜잭션 이메일 템플릿 변경
- 외부 도메인으로의 데이터 전송 코드 추가

## 변형 C — 마케터 버전

> **메모.** **이 CLAUDE.md는 우리 프로젝트의 시스템 오브 레코드입니다.** 채팅창에 쓴 지시는 사라지지만, 이 파일은 다음 세션의 시작점이 됩니다. 50~80줄을 넘기면 *주제별 문서로 분리*하세요.

### 1. 프로젝트 한 줄 정의
주간 1편의 블로그 글을 작성하고, 이를 SNS 3개 채널 콘텐츠와 뉴스레터 1통으로 자동 가공해 발행하는 콘텐츠 운영 에이전트 프로젝트입니다.

### 2. 사용 도구 스택
- 원고 작성: Claude (장문), Cursor (편집)
- 발행: 자체 블로그 (CMS) + 뉴스레터 발송 도구
- SNS: 링크드인, X, 스레드 (수동 게시 또는 예약 도구)
- 자산 저장: Notion (아이디어 큐 + 발행 일정)

### 3. 절대 하지 말 것 (하드 제약)
- 사람 검토 없이 SNS, 뉴스레터에 자동 발행 금지.
- 실제 고객사명, 사례를 가공 없이 인용 금지.
- 같은 글을 SNS 채널에 동일 문장으로 복붙 금지. 채널별 톤을 분리합니다.
- 통계 수치는 출처 없이 인용하지 마세요.
- 한 세션에서 발행 콘텐츠 5개를 초과해 만들지 마세요. 품질이 떨어집니다.

### 4. 자주 하는 작업과 검증 방법
- 블로그 초안 작성: 제목/요약/본문/CTA 4요소가 모두 있는지 확인합니다.
- SNS 가공: 채널별 글자 수 제한과 톤 가이드를 통과했는지 점검합니다.
- 뉴스레터 발송: 테스트 발송으로 본인 메일함에서 렌더링을 먼저 확인합니다.

### 5. 폴더/파일 컨벤션
- `/posts/YYYY-MM-DD_제목.md` — 블로그 원본
- `/snippets/YYYY-MM-DD_채널.md` — SNS용 가공본
- `/newsletters/YYYY-WW.md` — 주간 뉴스레터 원고
- `/ideas/idea-queue.md` — 아이디어 큐

### 6. 세션 시작 시 항상 확인할 것
- `ideas/idea-queue.md`에서 이번 주 우선 주제를 고릅니다.
- 지난 주 발행물의 반응(좋아요, 클릭 수)을 한 줄로 확인합니다.

### 7. 세션 종료 시 항상 남길 것
- 발행 예정 콘텐츠 목록을 `progress.md`에 정리합니다.
- 새 아이디어가 떠올랐다면 `idea-queue.md`에 한 줄씩 추가합니다.

### 8. 사람의 승인이 필요한 작업 (휴먼 인 더 루프)
- 모든 외부 발행 (블로그/SNS/뉴스레터 최종 송출)
- 유료 광고 카피 최종본
- 실명 사례, 인터뷰 인용
- 톤앤매너 가이드 변경

## AI 에이전트 행동 원칙 (Karpathy 4원칙)

> 아래 원칙은 Andrej Karpathy가 정리한 Claude Code 행동 가이드라인을 한국어 PM·빌더 맥락에 적용한 것입니다.

**1. 먼저 생각하기 (Think Before Coding)**
가정을 명시적으로 말하세요. 여러 해석이 가능하면 선택하지 말고 물어보세요.
더 단순한 방법이 있다면 먼저 말하세요.

**2. 단순하게 (Simplicity First)**
요청한 것만 구현하세요. 요청하지 않은 기능·추상화·유연성을 추가하지 마세요.
200줄로 쓸 수 있는 것을 50줄로 쓸 수 있다면 다시 작성하세요.

**3. 외과적으로 (Surgical Changes)**
필요한 코드만 건드리세요. 관련 없는 코드를 개선하지 마세요.
변경된 모든 줄은 사용자의 요청과 직접 연결되어야 합니다.

**4. 목표 주도 실행 (Goal-Driven Execution)**
성공 기준을 먼저 정의하세요. 다단계 작업은 검증 체크포인트와 함께 계획을 말하세요.
"됐습니다"는 검증이 확인한 후에만 말하세요.
